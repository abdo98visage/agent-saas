
خطة التنفيذ التقنية التفصيلية – مشروع Hermes Agent للشركة
إعداد: مهندس برمجيات أول (خبرة 20+ سنة في أنظمة المؤسسات عالية التوفر، العزل متعدد المستأجرين، وتطبيقات سطح المكتب)
الإصدار: 1.0
تاريخ الصلاحية: 2026-06-11 – 2026-12-31
الجمهور المستهدف: فريق التطوير، مهندسو DevOps، مديرو المشاريع التقنيون.

0. تعديلات مراجعة تقنية قبل بدء التنفيذ
هذه الخطة قابلة للتنفيذ، لكنها تحتاج ضبطاً حتى لا يتحول الإصدار الأول إلى مشروع واسع أكثر من اللازم. أفضل مسار هو بناء MVP إنتاجي صغير ثم التوسع على مراحل، مع بوابات قبول واضحة تمنع الانتقال بين المراحل قبل إثبات الأمان والتكلفة وتجربة المستخدم.

قرارات تقنية ملزمة للإصدار الأول:

1. اعتماد 12 أسبوعاً كجدول أساسي. أي ضغط إلى 8 أسابيع يتطلب حذف تلغرام أو KPIs أو auto-update من الإصدار الأول.
2. أولوية التنفيذ: Backend + Auth + Isolation، ثم Chat API مع مزود نماذج، ثم Desktop Client، ثم Admin، ثم Telegram/KPIs.
3. عدم إرسال محتوى المجلد كاملاً مع كل رسالة. يجب بناء فهرس محلي، واختيار المقاطع ذات الصلة بالاستعلام، ووضع حد رموز ثابت لكل طلب.
4. تخزين سياق الملفات في قاعدة البيانات يجب أن يكون محدوداً. يفضل تخزين metadata وملخصات ومقاطع مستخدمة فقط، وليس snapshot كامل لكل الملفات.
5. Electron يجب أن يعمل وفق إعدادات أمان صارمة: contextIsolation=true، nodeIntegration=false في renderer، preload API محدودة، Content Security Policy، وعدم تمرير مسارات ملفات عشوائية من renderer إلى main بدون تحقق.
6. RLS في PostgreSQL ليست اختياراً تجميلياً. يجب إما تنفيذها بشكل صحيح باستخدام app.current_user_id لكل معاملة، أو توثيق سبب تأجيلها مع اختبارات عزل إجبارية لكل endpoint.
7. لا تبدأ بـ WebSocket إلا إذا كانت تجربة streaming مطلوبة في MVP. polling أو Server-Sent Events يكفيان كبداية أبسط.
8. يجب إضافة cost guardrails: حد رموز لكل طلب، حد يومي، تنبيه عند 70% و90% من الحصة، وسجل تكلفة لكل مستخدم/قسم.
9. بوابة تلغرام لا يمكنها معرفة "المشروع الحالي" إلا إذا كان المشروع محفوظاً في الخادم أو مربوطاً بجلسة Desktop سابقة. لذلك أوامر /project و /files يجب أن تكون للقراءة فقط أو تؤجل بعد مزامنة آمنة.
10. كل مرحلة يجب أن تنتهي بعرض قابل للتجربة، اختبارات آلية أساسية، ومراجعة أمنية قصيرة قبل الانتقال للمرحلة التالية.

1. نظرة عامة على الخطة
هذه الخطة تحوّل متطلبات الأعمال (BRD) إلى مجموعة محددة من الأدوات، المكتبات، التقنيات، التكوينات، مهام التطوير، و إجراءات الضمان التي يجب تنفيذها لبناء نظام Hermes Agent بشكل صحيح، قابل للتوسع، وآمن، وسهل الصيانة.

المبادئ التوجيهية (Guiding Principles):

أقل قدر من التعقيد (KISS): لا نستخدم حاويات Linux لكل مستخدم، ولا نوزع config لكل موظف.

الأمان أولاً: عزل البيانات على مستوى قاعدة البيانات وليس نظام الملفات، تشفير المفاتيح الحساسة، تسجيل كل عملية حساسة.

قابلية التوسع: دعم 500 مستخدم في البداية، وصولاً إلى 2000 مستخدم باستخدام نفس المعمارية مع إضافة عقد.

صيانة منخفضة: تحديث الخادم المركزي يصل لجميع العملاء تلقائياً، لا حاجة لتدخل يدوي على أجهزة الموظفين.

2.2 قاعدة البيانات (مخطط تفصيلي)
جميع الجداول تستخدم user_id كـ Foreign Key لضمان العزل. سنضيف فهارس مركبة للتسريع.

sql
-- جدول المستخدمين (الموظفون والمشرفون)
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) NOT NULL UNIQUE,
    hashed_password VARCHAR(255) NOT NULL,
    full_name VARCHAR(100),
    department VARCHAR(50), -- marketing, hr, it, sales
    role VARCHAR(20) DEFAULT 'employee', -- admin, employee
    is_active BOOLEAN DEFAULT TRUE,
    max_tokens_per_day INT DEFAULT 50000,
    max_requests_per_day INT DEFAULT 200,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP
);
CREATE INDEX idx_users_department ON users(department);
CREATE INDEX idx_users_is_active ON users(is_active);

-- جدول جلسات المحادثة (session لكل موظف لكل مشروع أو لكل موضوع)
CREATE TABLE sessions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(255),
    agent_template_name VARCHAR(50), -- marketing, hr etc.
    created_at TIMESTAMP DEFAULT NOW(),
    last_activity TIMESTAMP
);
CREATE INDEX idx_sessions_user_id ON sessions(user_id);
CREATE INDEX idx_sessions_last_activity ON sessions(last_activity);

-- جدول الرسائل (التخزين الكامل للسياق)
CREATE TABLE messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id UUID NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    role VARCHAR(20) NOT NULL, -- user, assistant, system
    content TEXT NOT NULL,
    project_context TEXT, -- snapshot of files/folder at time of message
    tokens_used INT,
    created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_messages_session_id ON messages(session_id);
CREATE INDEX idx_messages_created_at ON messages(created_at);

-- جدول مؤشرات الأداء (مستوى التفاصيل: لكل رسالة)
CREATE TABLE kpis (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    date DATE NOT NULL,
    tasks_completed INT DEFAULT 0,
    messages_sent INT DEFAULT 0,
    avg_response_quality FLOAT, -- من 1 إلى 5، يتم تحديثه يدوياً أو تلقائياً
    active_minutes INT DEFAULT 0,
    tools_used JSONB -- ["web_search", "content_generator"]
);
CREATE INDEX idx_kpis_user_id_date ON kpis(user_id, date);

-- جدول قوالب الوكلاء (مركزي، يتحكم به المشرف)
CREATE TABLE agent_templates (
    name VARCHAR(50) PRIMARY KEY,
    department VARCHAR(50),
    system_prompt TEXT NOT NULL,
    tools JSONB, -- قائمة الأدوات المسموحة
    model_name VARCHAR(50) DEFAULT 'qwen3-14b',
    max_tokens_per_request INT DEFAULT 4000,
    temperature FLOAT DEFAULT 0.7
);

-- جدول ربط تلغرام (كل موظف يمكنه ربط حساب واحد)
CREATE TABLE telegram_bindings (
    user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    telegram_chat_id BIGINT NOT NULL UNIQUE,
    binding_token VARCHAR(64) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_telegram_chat_id ON telegram_bindings(telegram_chat_id);

-- جدول سجل التدقيق (audit log) – لا يحذف أبداً
CREATE TABLE audit_log (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID REFERENCES users(id), -- من قام بالعملية (قد يكون النظام)
    action VARCHAR(100) NOT NULL, -- "add_employee", "set_limits", "access_file"
    details JSONB,
    ip_address INET,
    created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_audit_user_id ON audit_log(user_id);
CREATE INDEX idx_audit_created_at ON audit_log(created_at);

python
async def call_minimax(messages: list, model: str, api_key: str):
    async with httpx.AsyncClient(timeout=60.0) as client:
        response = await client.post(
            "https://api.minimax.chat/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}"},
            json={
                "model": model,
                "messages": messages,
                "temperature": 0.7,
                "max_tokens": 4000
            }
        )
        return response.json()["choices"][0]["message"]["content"]

تدفق البيانات الأساسي:

الموظف يفتح Electron → يسجل الدخول (JWT token يحفظ محلياً مشفر).

يضغط "فتح مجلد" → يقرأ الملفات → يرسل session_id جديد أو موجود مع كل رسالة.

الطلب يصل FastAPI → يتأكد من user_id من JWT → يسجل في DB → يمرر إلى Celery Worker.

Celery Worker يطلب من MiniMax API باستخدام قالب الوكيل المناسب (حسب department) ومفتاح API الصحيح.

الرد يُحفظ في قاعدة البيانات ويُعاد إلى العميل عبر WebSocket (أو الـ client يسأل دورياً – نبدأ بـ polling ثم نحسن لاحقاً).
