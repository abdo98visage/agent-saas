# رحلة العميل داخل تطبيق سطح المكتب

هذا الملف يشرح رحلة الموظف داخل تطبيق سطح المكتب من أول تشغيل حتى الاستخدام اليومي، مع توضيح الوظائف التي تم اختبارها على الـ packaged EXE ضد Docker.

## 1. استلام التطبيق وبيانات التفعيل

1. المدير ينشئ موظفاً من لوحة الإدارة.
2. المدير يربط الموظف بـ profile مناسب.
3. المدير يرسل للموظف:
   - ملف تثبيت التطبيق أو ملف EXE.
   - invite token.
   - رابط API إذا كان مختلفاً عن الافتراضي.
4. الموظف يثبت التطبيق ويفتحه.

النتيجة المتوقعة:
- التطبيق يفتح بدون terminal.
- إذا لا يوجد token محفوظ، تظهر شاشة التفعيل.

## 2. تفعيل الحساب من التطبيق

1. الموظف يدخل invite token.
2. يدخل كلمة مرور جديدة.
3. يتأكد من API URL.
4. يضغط تفعيل الحساب.
5. التطبيق يرسل الطلب إلى `/api/auth/activate`.
6. عند نجاح التفعيل يحفظ التطبيق token محلياً.
7. تختفي شاشة التفعيل.

النتيجة المتوقعة:
- الحساب يصبح activated.
- token محفوظ في إعدادات التطبيق.
- التطبيق يبدأ تحميل المحادثات.
- التطبيق يحاول فتح WebSocket مع المنصة.

## 3. الاتصال بالمنصة

1. التطبيق يقرأ API URL من `desktop-config.json` أو من الإعدادات.
2. يستخدم API URL لطلبات REST.
3. يطلب WebSocket token قصير المدة من `/api/auth/ws-token`.
4. يفتح WebSocket على `/api/chat/ws/chat`.
5. يرسل heartbeat بشكل دوري.

النتيجة المتوقعة:
- WebSocket يعمل ضد نفس API URL بدون تكرار `/api`.
- التطبيق جاهز لإرسال الرسائل.

## 4. إرسال رسالة من التطبيق

1. الموظف يكتب رسالة.
2. يضغط زر الإرسال أو Enter.
3. التطبيق يضيف رسالة المستخدم في الواجهة.
4. إذا WebSocket مفتوح:
   - يرسل الرسالة مباشرة.
   - يعرض typing indicator.
   - يستقبل start/chunk/done.
   - يعرض رد المساعد تدريجياً.
5. إذا WebSocket غير متاح:
   - يحفظ الرسالة في offline queue.
   - يحاول إعادة الاتصال.

النتيجة المتوقعة:
- الرد يظهر داخل التطبيق.
- المحادثة تحفظ في backend.
- تظهر المحادثة في القائمة الجانبية.
- المدير يستطيع رؤيتها من لوحة الإدارة.

## 5. تحميل المحادثات السابقة

1. بعد تسجيل الدخول أو التفعيل، التطبيق يستدعي `/api/chat/conversations`.
2. يعرض المحادثات في الشريط الجانبي.
3. عند اختيار محادثة يستدعي `/api/chat/conversations/{id}/messages`.
4. يعرض رسائل المستخدم والمساعد.

النتيجة المتوقعة:
- الموظف يستطيع الرجوع للمحادثات السابقة.
- الرسائل تظهر بنفس الترتيب المحفوظ في النظام.

## 6. استخدام سياق المشروع

1. الموظف يفتح لوحة الإعدادات.
2. يختار مجلد مشروع.
3. التطبيق يفحص الملفات النصية المسموح بها.
4. يستبعد:
   - `.env`
   - مفاتيح وشهادات مثل `.pem`, `.key`, `.p12`, `.pfx`, `.crt`
   - الملفات الكبيرة جداً
   - مجلدات مثل `node_modules`, `.git`, `dist`, `.venv`
5. يستطيع الموظف تحديد ملفات معينة كأولوية.
6. عند إرسال رسالة، التطبيق يبني project context من الملفات المناسبة.
7. يرسل context مع الرسالة إلى Hermes عبر API.

النتيجة المتوقعة:
- المساعد يحصل على سياق المشروع.
- الملفات الحساسة لا تدخل في الفحص.
- حجم السياق محدود حتى لا يستهلك tokens بشكل عشوائي.

## 7. قراءة وتعديل ملف من التطبيق

1. الموظف يختار ملفاً من قائمة ملفات المشروع.
2. التطبيق يقرأ الملف ويعرضه في المحرر.
3. الموظف يعدل المحتوى.
4. يضغط Preview Save.
5. التطبيق ينشئ preview token ويعرض ملخص التغيير:
   - عدد الأسطر قبل التعديل
   - عدد الأسطر بعد التعديل
   - عدد الأسطر المتغيرة
6. بعد المراجعة يضغط Apply Save.
7. التطبيق يكتب الملف على القرص.

النتيجة المتوقعة:
- لا يتم حفظ التعديل بدون preview.
- لا يمكن الكتابة خارج مجلد المشروع المختار.
- التعديل يطبق فقط بعد موافقة الموظف.

## 8. Offline Queue

1. إذا كتب الموظف رسالة والاتصال غير متاح، التطبيق يحفظها محلياً.
2. تظهر في badge باسم queued.
3. عند عودة WebSocket، التطبيق يحاول إرسال الرسائل المعلقة.
4. يستطيع الموظف مسح الرسائل المعلقة من الإعدادات.

النتيجة المتوقعة:
- الرسائل لا تضيع عند انقطاع الاتصال.
- يمكن رؤية عدد الرسائل المعلقة.
- يمكن مسح queue عند الحاجة.

## 9. ربط Telegram من التطبيق

1. الموظف يفتح الإعدادات.
2. يضغط توليد كود.
3. التطبيق يستدعي `/api/telegram/generate-bind-code`.
4. يظهر bind code داخل التطبيق.
5. الموظف يرسل `/bind <code>` إلى Telegram bot.
6. يضغط تأكيد الربط.
7. التطبيق يستدعي `/api/telegram/bind-with-code`.

النتيجة المتوقعة:
- Telegram chat id يرتبط بحساب الموظف.
- بعد الربط يمكن استخدام Telegram كواجهة إضافية لنفس الحساب.

## 10. تحديثات التطبيق

1. التطبيق يقرأ `UPDATE_FEED_URL` إذا كان مضبوطاً.
2. إذا لم يكن مضبوطاً، يعرض أن التحديثات غير configured.
3. عند وجود feed في بيئة الإنتاج يمكن فحص التحديثات.

النتيجة المتوقعة في Docker/local:
- update status يظهر `not_configured`.

النتيجة المتوقعة في الإنتاج:
- إذا تم إعداد feed صحيح، يستطيع التطبيق فحص التحديثات.

## 11. الأمان داخل تطبيق سطح المكتب

التطبيق يستخدم:

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- منع فتح نوافذ خارجية عشوائية
- منع navigation غير مقصود
- Content Security Policy
- IPC محدود من preload
- منع قراءة ملفات خارج workspace المختار
- منع تضمين ملفات secrets في project scan

## 12. ما تم اختباره فعلياً على packaged EXE

تم تشغيل ملف:

`desktop/dist/win-unpacked/FQ-SaaS Workspace.exe`

واختبار:

- فتح التطبيق كـ packaged EXE.
- ظهور شاشة التفعيل عند أول تشغيل.
- تفعيل الموظف باستخدام invite token حقيقي من Docker.
- حفظ token والإعدادات.
- فتح WebSocket حقيقي ضد Docker API.
- إرسال رسالة chat واستقبال Hermes response.
- إنشاء conversation في backend.
- scanFolder لمجلد مشروع حقيقي.
- استبعاد `.env`.
- readFile.
- buildProjectContext.
- prepareFileWrite.
- applyFileWrite.
- Telegram bind UI flow.
- offlineQueue persistence.
- update status.

## 13. المسار اليومي للموظف

1. يفتح الموظف التطبيق.
2. التطبيق يتصل تلقائياً بالمنصة.
3. الموظف يختار أو يبدأ محادثة.
4. يختار مجلد المشروع عند الحاجة.
5. يرسل أسئلة أو أوامر للمساعد.
6. يراجع الردود.
7. إذا احتاج تعديل ملف:
   - يفتح الملف.
   - يراجع التعديل.
   - يطبق الحفظ بعد preview.
8. يستخدم Telegram إذا كان مربوطاً.
9. المدير يراقب الاستخدام من المنصة.

## 14. ما يحتاج إعدادات حقيقية في الإنتاج

هذه الأشياء جاهزة من ناحية التطبيق، لكنها تعتمد على بيئة الإنتاج:

- API URL النهائي على VPS.
- شهادة TLS صحيحة.
- Telegram bot الحقيقي.
- LLM API key الحقيقي في المنصة.
- update feed إذا أردت auto updates.
- code signing certificate رسمي للـ EXE.
