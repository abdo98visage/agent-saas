# خطة إغلاق مخاطر الاستقرار واختبار قبول المستخدم النهائي

**التاريخ:** 2026-08-04  
**النطاق:** Dashboard، FastAPI، Desktop Application، Hermes Runtime، WebSocket، المحادثات، Knowledge، MCP، الملفات، الجلسات، المهام الخلفية، التحديث والاستعادة  
**الهدف:** إثبات أن تجربة المستخدم مستقرة وصحيحة عند استخدام الشركة للمنصة فعلياً، وليس فقط نجاح endpoints أو اختبارات منفردة.

## 1. الخلاصة التنفيذية

الاختبارات الحالية تثبت أن المسارات الأساسية تعمل، لكنها لا تكفي وحدها لضمان تجربة شركة كاملة. ما ينقص لإعطاء ثقة عالية قبل تسليم المنصة هو اختبار قبول متعدد المستخدمين، واختبار استمرار لعدة ساعات، واختبارات أعطال مقصودة أثناء الاستخدام الحقيقي.

لا يوجد نظام برمجي يمكن ضمان خلوه من كل خطأ، كما لا يمكن ضمان صحة أي نموذج لغوي بنسبة 100% في الأسئلة المفتوحة. الهدف الصحيح هو:

- منع الأعطال الصامتة وفقدان الرسائل وخلط المحادثات.
- منع تسرب بيانات مستخدم إلى مستخدم آخر بنسبة 100%.
- قياس جودة الإجابات في الحالات التي لها إجابة متوقعة.
- إظهار خطأ مفهوم وقابل للاسترداد عند تعطل مزود النموذج أو MCP بدلاً من تعليق التطبيق.
- إثبات أن الخدمات تتعافى بعد restart أو انقطاع مؤقت.
- عدم اعتماد الإصدار إذا بقي خلل يؤثر على المستخدم النهائي.

قرار Production لا يعتمد على عبارة «الاختبار نجح» فقط، بل على تحقيق معايير القبول الرقمية في هذه الوثيقة وإغلاق كل عيوب `S0` و`S1`.

## 2. المخاطر التي يجب إثبات إغلاقها

### 2.1 انقطاع تجربة المستخدم

- WebSocket ينقطع ويبقى التطبيق معلقاً.
- Runtime أو Orchestrator يصبح غير متاح ولا يتعافى.
- الطلب ينتهي في الخادم لكن Desktop لا يعرض النتيجة.
- المستخدم يرسل رسالة أثناء الانقطاع فتضيع أو تتكرر بعد عودة الاتصال.
- التطبيق يبقى في حالة typing/streaming دون نهاية أو رسالة خطأ.

### 2.2 خطأ الإجابة

- النموذج يجيب بمعلومة غير موجودة في Knowledge.
- يستشهد بمصدر غير صحيح أو يخترع citation.
- يستخدم Knowledge غير مصرح بها للمستخدم.
- يتجاهل Profile أو يستخدم مزوداً أو تعليمات تخص Profile آخر.
- يعرض فشل الأداة كأنه نتيجة صحيحة.

### 2.3 نسيان أو خلط المحادثة

- الرد على سؤال سابق بدلاً من آخر رسالة.
- استخدام رسائل من Conversation أخرى للمستخدم نفسه.
- استخدام رسائل أو ملفات مستخدم آخر.
- نسيان حقيقة أساسية بعد محادثة طويلة.
- إعادة offline message إلى Conversation أو Project مختلف.

### 2.4 فشل الجلسة

- انتهاء access token يخرج الموظف من التطبيق.
- refresh rotation يفشل عند وجود أكثر من request في الوقت نفسه.
- restart للتطبيق يفقد الجلسة أو المحادثات.
- إبطال المستخدم من المدير لا يطبق، أو يطبق على مستخدم آخر.

### 2.5 فشل التكاملات

- MCP المتعطل يعطل المحادثة العادية.
- approval يطبق على عملية أو مستخدم مختلف.
- Knowledge sync يمحو آخر نسخة سليمة بسبب ملف تالف أو share غير متاح.
- Attachment يفشل بصمت أو يصل إلى Conversation خاطئة.

### 2.6 تدهور الأداء

- مستخدم واحد يحتكر Runtime ويوقف الآخرين.
- تراكم الطلبات يرفع زمن الإجابة باستمرار.
- memory أو عدد العمليات أو temporary directories يزداد دون عودة.
- Redis أو PostgreSQL connections تنفد بمرور الوقت.

## 3. ملاحظة تقنية حرجة يجب اختبارها

المنصة ترسل حالياً آخر **20 رسالة** من سجل المحادثة إلى Runtime. هذا يحمي حجم السياق، لكنه قد يجعل حقيقة ذُكرت فقط في بداية محادثة طويلة خارج النافذة الحالية.

لذلك يجب عدم الاكتفاء باختبار محادثة من رسالتين. سيتم اختبار المرجع الأساسي بعد الرسائل:

- 5
- 19
- 21
- 30
- بعد إغلاق Desktop وفتحه مجدداً
- بعد restart للـAPI وRuntime

إذا نسي Agent المرجع المطلوب بعد تجاوز 20 رسالة، فهذه ليست نتيجة قبول. يجب عندها تنفيذ أحد الحلول المحدودة التالية قبل إعادة الاختبار:

1. conversation summary محفوظة في الخادم ومضافة للسياق.
2. استرجاع الرسائل ذات الصلة من نفس Conversation.
3. زيادة النافذة فقط إذا أثبت قياس tokens والكلفة أنها كافية وآمنة.

لا يتم اختيار الحل قبل ظهور نتيجة القياس، ولا يتم اعتبار «النموذج نسي» عذراً مقبولاً في سيناريو عمل مطلوب.

## 4. بيئة الاختبار المطلوبة

### 4.1 البنية

- خادم Staging مطابق لتوزيعة On-Premise النهائية.
- نفس Docker images وdigests التي ستُسلّم للعميل.
- PostgreSQL وRedis وAPI وWorker وBeat وOrchestrator وRuntime وDashboard.
- DNS وTLS مطابقان تقريباً للإنتاج، وليس `localhost` فقط.
- مزود نموذج حقيقي بالموديل الفعلي المراد بيعه.
- MCP حقيقي واحد على الأقل، ومصدر Knowledge محلي واحد.
- مراقبة Prometheus/logs/audit مفعلة.

### 4.2 أجهزة المستخدمين

الأفضل استخدام أربعة أجهزة Windows أو أربع VMs منفصلة. إذا تعذر ذلك، تستخدم أربع حسابات Windows وAppData منفصلة، مع عدم مشاركة token أو settings أو workspace.

كل موظف يستخدم نسخة Desktop المعبأة نفسها المرشحة للإنتاج. لا يعتمد اختبار القبول على استدعاءات API وحدها.

### 4.3 البيانات

- قاعدة بيانات جديدة أو snapshot معروف قبل كل جولة.
- Profile مستقل لكل شخصية.
- Knowledge وMCP assignments مختلفة بين المستخدمين.
- Workspace محلي مستقل لكل مستخدم.
- عدم استخدام بيانات عملاء حقيقية.

### 4.4 أدوات الاختبار التي يجب بناؤها قبل الجولة

الأدوات الحالية تختبر Desktop واحداً، و`load_test.py` يستخدم حساباً واحداً. هذا لا يثبت العزل أو العدالة بين أربعة موظفين. الحد الأدنى المطلوب، مع إعادة استخدام CDP والسكربتات الموجودة، هو:

#### Multi-user Desktop runner

- تشغيل أربع نسخ من البرنامج المعبأ في الوقت نفسه.
- `user-data-dir` وAppData وworkspace وremote debugging port مستقلة لكل نسخة.
- تجهيز الحسابات وProfiles من Admin API، ثم التفاعل من واجهة Desktop نفسها.
- عدم اعتبار system/error element إجابة ناجحة؛ النجاح يتطلب assistant content و`done` فعليين.
- حفظ نتيجة كل خطوة كـJSONL مع user وconversation وclient message وtimestamps.

#### Scenario manifest

ملف بيانات يحدد لكل شخصية:

- prompts.
- golden answers أو rubric.
- canary المسموح.
- canaries الممنوعة.
- citation المتوقع.
- Profile وKnowledge وMCP المتوقعان.
- timeout ومعيار النجاح.

هذا يفصل بيانات الاختبار عن كود التشغيل ويجعل إعادة الجولة مطابقة بعد كل إصلاح.

#### Multi-user load runner

- توسيع load test لقبول ملف أربعة مستخدمين بدلاً من token واحدة.
- Conversation مستقلة لكل worker.
- التحقق من assistant chunks و`done` ومحتوى غير فارغ، وليس HTTP 200 فقط.
- قراءة History بعد الجولة ومقارنة عدد وترتيب الرسائل.
- حساب fairness لكل مستخدم، لا المتوسط العام فقط.

#### Fault-injection runner

- أوامر محدودة ببيئة Staging لإعادة تشغيل خدمة واحدة أو قطع شبكة عميل واحد.
- health gate قبل الحالة وبعدها.
- rollback تلقائي لحالة الشبكة والخدمة حتى عند فشل السكربت.
- منع تشغيله إذا كان environment أو hostname يشير إلى Production.

#### Evidence collector

- جمع `/api/metrics` وservice health وDocker stats وDB/Redis counters كل 5 دقائق.
- ربط الأخطاء بالـcorrelation/trace IDs.
- تنقية prompts والمفاتيح من التقرير.
- إخراج تقرير Markdown وJSON بالنتائج والـpercentiles والعيوب.

لا نحتاج إطار UI جديداً أو منصة اختبار تجارية لهذه الجولة؛ يمكن توسيع أدوات CDP وPowerShell وPython الموجودة بأقل كود ممكن.

### قاعدة canary

كل رمز يزرع فقط في بيانات مستخدمه. ظهور أي رمز في إجابة مستخدم آخر يعني تسرباً بين المستخدمين ويوقف الاختبار فوراً.

## 6. تصنيف العيوب وقرار الإيقاف

| الدرجة | التعريف | القرار |
|---|---|---|
| `S0` | تسرب بيانات/سر، خلط مستخدمين، تنفيذ Terminal/Code، تغيير ملف بلا موافقة، فساد بيانات | إيقاف فوري وNo-Go |
| `S1` | فقد رسالة، تكرار عملية، Conversation خاطئة، Agent غير متاح، جواب حرج خاطئ، تعليق لا يتعافى | No-Go حتى الإصلاح وإعادة الجولة كاملة |
| `S2` | خطأ قابل للاسترداد لكن يربك المستخدم أو يتكرر بصورة ملحوظة | إصلاح قبل Pilot أو قبول استثنائي موثق ومحدود |
| `S3` | ملاحظة شكلية لا تؤثر على الوظيفة | لا تغيّر التصميم ضمن هذه الخطة |

يوقف الاختبار فوراً عند:

- ظهور canary لمستخدم آخر.
- وصول Knowledge أو MCP غير مصرح بهما.
- تنفيذ terminal/code execution.
- رسالة حفظت في Conversation مختلفة.
- عملية ملف تمت دون approval المطلوبة.
- تعديل أو كسر Audit chain.
- فقد أو تكرار رسالة مالية/وظيفية.

## 7. معايير القبول الرقمية

### الأمان والعزل

- تسرب بيانات بين المستخدمين: **0**.
- وصول غير مصرح إلى Knowledge/MCP: **0**.
- Terminal أو Code Execution: **0**.
- citations مختلقة في أسئلة Knowledge: **0**.
- عمليات ملفات دون approval المطلوبة: **0**.

### الاستقرار

- الجولات المتزامنة في UAT: **صفر فشل غير مسترد**.
- نجاح الطلبات في soak test: **≥ 99.5%**، مع استبعاد الأعطال المحقونة المتوقعة فقط.
- WebSocket reconnect بعد عودة الشبكة: **≤ 15 ثانية**.
- تعافي API بعد restart: **≤ 30 ثانية**.
- تعافي Orchestrator/Runtime بعد restart: **≤ 60 ثانية**.
- عدم بقاء spinner/streaming دون نتيجة أو خطأ لأكثر من **90 ثانية**.
- الرسائل المعلقة بعد reconnect: ترسل **مرة واحدة فقط**.
- temporary runtime directories بعد الجولة: **0**.

### الأداء

- زمن أول استجابة مرئية، p95: **≤ 10 ثوانٍ** في البنية المتفق عليها.
- زمن إكمال الرد العادي، p95: **≤ 60 ثانية**.
- لا يوجد طلب عادي يتجاوز **90 ثانية** دون نتيجة مفهومة.
- لا يزيد p95 في الساعة الأخيرة من soak بأكثر من **20%** عن الساعة الأولى.
- لا يوجد نمو مستمر غير مبرر في الذاكرة أو العمليات أو اتصالات DB/Redis.

### صحة الإجابة

- أسئلة الحقائق المحددة من Knowledge: **≥ 95%** عبر التكرارات، و**100%** للسياسات الحرجة.
- صحة citation وربطه بالمصدر الصحيح: **100%**.
- إجابات الحسابات ذات golden answer: **100%** ضمن tolerance المحدد.
- التزام Profile الصحيح: **100%**.
- الرفض الصحيح عند غياب المعلومة بدلاً من اختراعها: **100%** للحالات المعدة.
- السيناريوهات المفتوحة: تقييم بشري لا يقل عن `4/5` في **95%** من الحالات.

### استمرارية المحادثة

- عدم الخلط بين Conversations: **100%**.
- تذكر المرجع المطلوب في النقاط 5 و19 و21 و30: **100%** بعد تطبيق السلوك المعتمد.
- بعد إعادة فتح Desktop أو restart للخدمات: الرسائل والترتيب وConversation ID متطابقة.
- لا توجد assistant answer مرتبطة برسالة أقدم بدلاً من أحدث رسالة.

## 8. مراحل التنفيذ

## المرحلة 0 — تثبيت المرشح وإعداد القياس

### التنفيذ

1. تثبيت release candidate واحد وعدم تغيير الصور أثناء الجولة.
2. تسجيل digests وschema revision وإصدار Desktop.
3. إنشاء المدير والموظفين الأربعة وProfiles وcanaries.
4. تجهيز مجلد مستقل لكل Desktop.
5. تجهيز Knowledge source وMCP الحقيقي.
6. التقاط baseline لعدد العمليات والذاكرة وDB connections وRedis وtemporary directories.
7. مزامنة الوقت على الخادم والأجهزة لربط الأحداث بالـtrace IDs.

### التحقق

- جميع الخدمات `healthy/ready`.
- Dashboard يعرض الموظفين الأربعة.
- كل Desktop يفتح بحساب مختلف.
- كل Profile يعرض policy الفعلية الصحيحة.
- قاعدة البيانات وAudit chain سليمتان.

### بوابة الانتقال

لا تبدأ UAT إذا كان أي مستخدم يشارك token أو AppData أو Workspace مع مستخدم آخر.

## المرحلة 1 — Golden Journeys منفردة

تُنفذ الرحلة كاملة لكل موظف منفرداً قبل التزامن لعزل الأخطاء الأساسية.

### لكل مستخدم

1. التفعيل أو login.
2. إغلاق Desktop وفتحه والتأكد من استمرار الجلسة.
3. إنشاء Conversation جديدة.
4. إرسال سؤال قصير وسؤال عربي وسؤال إنجليزي.
5. فتح Conversation قديمة والمتابعة منها.
6. إنشاء Conversation ثانية والتبديل بينهما.
7. سؤال Knowledge مع citation.
8. سؤال لا توجد إجابته والتأكد من عدم الاختلاق.
9. اختبار الملف أو MCP حسب الشخصية.
10. التأكد من ظهور run في Dashboard وربطه بالمستخدم الصحيح.

### التحقق

- مقارنة UI مع DB messages وAgentRun events.
- الترتيب وعدد الرسائل متطابقان.
- Profile وprovider وconversation_id صحيحة.
- لا يوجد canary لغير المستخدم.

### الاختبارات بعد المرحلة

- backend suite.
- Desktop unit tests.
- smoke test.
- packaged Desktop E2E.

## المرحلة 2 — صحة Agent المتكررة

### مجموعة التقييم

لكل Profile تُعد 20 حالة على الأقل:

- 8 أسئلة Knowledge ذات إجابة exact.
- 4 حالات يجب أن يرفض فيها Agent التخمين.
- 3 حالات multi-turn.
- حالتان بالعربية وحالتان بالإنجليزية على الأقل.
- 2 حالات حساب/تنسيق ذات golden output.
- حالة prompt injection داخل document للتأكد من عدم تغيير policy.

كل حالة محددة تُشغل **3 مرات** لاكتشاف التذبذب؛ لا يكفي نجاح محاولة واحدة.

### ما يتم قياسه

- answer match أو rubric score.
- citation validity.
- provider/profile الصحيح.
- latency وtokens والكلفة.
- تباين النتائج بين المحاولات.
- عدم ادعاء نجاح MCP عند فشله.

### بوابة الانتقال

لا يبدأ اختبار التزامن إذا فشل أي سؤال سياسة حرجة أو ظهر citation مختلق.

## المرحلة 3 — محادثات طويلة وعدم النسيان

### السيناريو

لكل مستخدم Conversation مستقلة تحتوي في أول رسالة على مرجع canary وتعليمة عمل مهمة. تستمر المحادثة إلى 30 رسالة متنوعة.

عند الرسائل 5 و19 و21 و30 يسأل المستخدم سؤال متابعة قصيراً مثل «طبّق نفس القاعدة على المثال الجديد» دون إعادة كامل السياق.

### حالات إضافية

- إغلاق وفتح Desktop عند الرسالة 10.
- تبديل Conversation عند الرسالة 15 ثم العودة.
- restart للـAPI بعد الرسالة 22.
- restart للـRuntime بعد الرسالة 25.
- Attachment جديد عند الرسالة 27 للتأكد من عدم استبدال المرجع السابق خطأً.

### التحقق

- لا يستخدم Agent canary من Conversation ثانية.
- لا يجيب عن الرسالة السابقة بعد إرسال التالية.
- الرسائل محفوظة بالترتيب الصحيح.
- لا توجد رسالة user أو assistant مكررة.
- إن فشل التذكر بعد حدود الـ20 رسالة، ينفذ remediation ثم تعاد المرحلة من البداية.

## المرحلة 4 — UAT حي: مدير و4 موظفين في الوقت نفسه

### مدة الجولة

- 30 دقيقة warm-up.
- ساعتان استخدام فعلي متزامن كحد أدنى.
- 30 دقيقة تحقق نهائي ومراجعة Dashboard.

### جدول المحاكاة

#### الدقائق 0–30

- المدير يراجع status وpresence وassignments.
- الموظفون الأربعة يسجلون الدخول ويفتحون Conversations مستقلة.
- كل موظف يرسل 3 رسائل ويتحقق من History.

#### الدقائق 30–60

- الأربعة يرسلون رسالة في نافذة 10 ثوانٍ لقياس التزامن الحقيقي.
- A ينفذ سؤالاً حسابياً.
- B يرسل Attachment.
- C يبدل بين محادثتين.
- D يستدعي MCP ويقبل approval واحدة ويرفض أخرى.

#### الدقائق 60–90

- المدير يعدل Knowledge لـA فقط.
- المدير يسحب MCP من D أثناء بقاء Desktop مفتوحاً.
- المستخدمون الآخرون يستمرون في المحادثة.
- يتم التأكد من أن revoke لا يؤثر على B أو C ولا يبقي الاتصال متاحاً لـD.

#### الدقائق 90–120

- قطع شبكة C لمدة دقيقتين أثناء وجود رسالة جاهزة للإرسال.
- إعادة الشبكة والتحقق من offline queue وexactly-once.
- إغلاق Desktop لـB وفتحه والعودة إلى المحادثة نفسها.
- استمرار A وD في الطلبات أثناء ذلك.

#### الدقائق 120–150

- تعطيل C من Dashboard والتحقق من إغلاق وصوله فقط.
- إعادة تفعيل C/login بصورة طبيعية.
- الأربعة يرسلون burst أخيراً.
- المدير يراجع alerts وruns وusage وonline presence.

### دور المراقب

لكل رسالة يسجل:

- المستخدم وConversation ID.
- client message ID إن وجد.
- وقت الإرسال وأول chunk وdone.
- النتيجة: صحيح/خاطئ/تعليق/تكرار.
- citation أو MCP events.
- correlation/trace ID.

### بوابة الانتقال

صفر `S0` وصفر `S1`. ظهور `S1` يتطلب إصلاحه وإعادة الجولة المتزامنة كاملة، لا إعادة الحالة وحدها.

## المرحلة 5 — اختبارات الأعطال المقصودة

تنفذ حالة واحدة في كل مرة مع وجود موظفين يستخدمون المنصة، ثم تعاد الخدمات إلى baseline قبل الحالة التالية.

### 5.1 انقطاع شبكة Desktop

- قطع الشبكة قبل الإرسال.
- قطعها بعد start وقبل done.
- قطعها بعد done وقبل تحديث History.
- التحقق من reconnect وعدم التكرار واستعادة المحادثة من الخادم.

### 5.2 restart للـAPI

- أثناء عدم وجود طلبات.
- أثناء 4 WebSocket sessions.
- أثناء إنشاء Conversation.
- معيار القبول: reconnect تلقائي، لا فساد، ولا خلط.

### 5.3 restart للـOrchestrator

- أثناء طلب عادي.
- أثناء stream.
- يجب أن يحصل المستخدم على نتيجة أو خطأ واضح retryable، ثم ينجح الطلب التالي دون إعادة تشغيل Desktop.

### 5.4 restart للـRuntime

- أثناء run واحد وأثناء 4 runs.
- التأكد من تنظيف العمليات المؤقتة والقدرة على تنفيذ run جديد.
- لا يجوز عرض partial response كإجابة مكتملة.

### 5.5 Redis/Worker/Beat

- restart لـRedis والتحقق من rate limit والمهام والـpresence بعد التعافي.
- restart لـWorker أثناء durable task والتحقق من lease/retry/idempotency.
- restart لـBeat والتأكد من عدم تكرار scheduled task.

### 5.6 PostgreSQL مؤقتاً

- قطع الاتصال لمدة قصيرة في بيئة Staging فقط.
- يجب ألا يعلن readiness أن النظام جاهز أثناء الانقطاع.
- بعد العودة، لا توجد رسائل نصف محفوظة أو audit chain مكسورة.

### 5.7 مزود النموذج

- timeout.
- HTTP 429.
- HTTP 500.
- استجابة malformed.
- مفتاح غير صالح.

معيار القبول: رسالة مفهومة للمستخدم، لا hallucinated success، لا spinner دائم، والطلب التالي ينجح بعد عودة المزود.

### 5.8 MCP

- MCP غير متاح قبل الطلب.
- انقطاعه أثناء tool call.
- انتهاء approval timeout.
- approve ثم محاولة replay.
- revoke أثناء جلسة Desktop.

معيار القبول: يفشل MCP وحده، وتبقى المحادثة العادية والمنصة تعملان.

### 5.9 Knowledge source

- share غير متاح.
- ملف غير UTF-8.
- ملف أكبر من الحد.
- حذف ملف.
- محاولة symlink خارج الجذر.
- محتوى يحوي secret وprompt injection.

معيار القبول: لا تسرب، لا فهرسة خارج ACL، وحالة المصدر تظهر بوضوح دون حذف بيانات سليمة بصمت.

## المرحلة 6 — انتهاء الجلسة والاستمرار الطويل

### التنفيذ

في بيئة الاختبار تخفض مدة access token مؤقتاً إلى 2–5 دقائق مع إبقاء refresh policy نفسها، لتجنب انتظار 8 ساعات.

يُختبر:

- refresh أثناء REST request.
- refresh أثناء إعادة فتح WebSocket.
- طلبان يحصلان على 401 في الوقت نفسه.
- إغلاق Desktop وفتحه بعد انتهاء access token.
- rotation عدة مرات.
- إبطال session من المدير.
- انتهاء refresh token أو إلغاؤه.

### معايير القبول

- الموظف الطبيعي لا يعاد إلى activation بسبب انتهاء access token.
- refresh يستخدم مرة واحدة بصورة آمنة ولا يسبب سباقاً.
- عند الإبطال الإداري فقط، تظهر شاشة login/activation المناسبة.
- المستخدمون الآخرون لا تتأثر جلساتهم.

## المرحلة 7 — Soak Test

### المساران

#### مسار البنية الطويل

- مدة: 12 ساعة كحد أدنى، و24 ساعة قبل أول عميل كبير.
- 4 مستخدمين متزامنين.
- رسالة لكل مستخدم كل 1–3 دقائق مع فتح/إغلاق Conversations وKnowledge وMCP بصورة دورية.
- يمكن استخدام مزود محلي مضبوط للكلفة في معظم الدورة.

#### مسار النموذج الحقيقي

- ساعتان إلى 4 ساعات بالمزود والموديل الإنتاجي الفعلي.
- حالات correctness مختارة، لا مجرد نصوص performance.

### القياسات كل 5 دقائق

- success/error/timeout counts.
- p50/p95/max latency.
- active WebSockets.
- API/Runtime process memory وCPU على مستوى الخدمة.
- DB connections وlocks.
- Redis memory وqueue depth.
- Celery active/retried/dead-letter tasks.
- Runtime temporary directories والعمليات الفرعية.
- Audit chain status.
- Agent quality sample كل ساعة.

### معايير القبول

- لا memory/process leak مستمر.
- لا degradation أكبر من 20%.
- لا stuck runs أو approvals.
- لا orphan sessions أو temporary workspaces.
- نسبة النجاح ضمن الهدف.
- restart تلقائي لأي خدمة لا يسبب فقد بيانات.

## المرحلة 8 — السعة والضغط الآمن

الهدف ليس أرقاماً كبيرة عشوائية، بل معرفة الحد الآمن للشركة.

### مستويات الاختبار

1. 4 مستخدمين، run متزامن لكل مستخدم.
2. 8 طلبات متزامنة كـburst احتياطي.
3. تدرج حتى أول نقطة تدهور واضحة، من دون اختبار تدميري على الإنتاج.

### المطلوب

- REST وWebSocket مع مستخدمين مستقلين، لا token واحدة.
- أسئلة قصيرة وطويلة وKnowledge وMCP.
- قياس queueing وليس latency فقط.
- التأكد من عدالة الخدمة بين المستخدمين.

### مخرج المرحلة

- رقم `supported concurrent active runs` للعتاد المختبر.
- p95 عند السعة الاسمية.
- نقطة التدهور.
- توصية server sizing خاصة بالعميل.

لا يُكتب في عرض البيع رقم مستخدمين متزامنين قبل نجاح هذه المرحلة على عتاد مماثل.

## المرحلة 9 — Upgrade وBackup/Restore من منظور المستخدم

### Upgrade

- أربعة Desktop sessions مفتوحة قبل الترقية.
- تنفيذ النسخة الاحتياطية والترقية بالطريقة الرسمية.
- قياس مدة عدم التوفر.
- فتح التطبيق بعد الترقية والتحقق من login وHistory وKnowledge وMCP.
- فشل postflight تجريبي للتحقق من rollback.

### Backup/Restore

- إنشاء Conversations وKnowledge وMCP assignments بعد snapshot معروف.
- أخذ backup مشفر.
- الاستعادة في بيئة فارغة.
- دخول الموظفين الأربعة بالنسخة المستعادة.
- مقارنة users/profiles/messages/runs/audit/knowledge counts وattachments.
- إعادة سؤال متابعة من Conversation قديمة.

### معيار القبول

- لا فقد في البيانات الموجودة ضمن RPO المعتمد.
- Audit chain سليمة.
- المستخدم يستطيع متابعة محادثته بعد الاستعادة.
- لا ACL أو MCP assignment يتغير.

## المرحلة 10 — Pilot Acceptance

بعد نجاح الجولات الفنية، يُجرى Pilot لمدة 3–5 أيام مع 3–4 مستخدمين داخليين حقيقيين قبل أول عميل.

كل مستخدم يسجل يومياً:

- هل وصل إلى هدفه؟
- هل اضطر لإعادة السؤال؟
- هل اختلطت عليه Conversation؟
- هل ظهر انتظار غير مفهوم؟
- هل الإجابة صحيحة ومسنودة؟
- هل احتاج تدخلاً من المدير؟

تعقد مراجعة يومية قصيرة للعيوب والقياسات، ولا يُسمح بإضافة ميزات جديدة أثناء Pilot. الهدف الاستقرار فقط.

## 9. حلقة الإصلاح وإعادة الاختبار

لكل عيب:

1. حفظ خطوات التكرار ووقت الحدث والمستخدم وConversation ID وtrace ID.
2. تحديد الطبقة: Desktop/API/DB/Orchestrator/Runtime/provider/MCP/Knowledge.
3. كتابة regression test يفشل قبل الإصلاح.
4. تنفيذ أقل إصلاح ممكن دون تغيير التصميم أو الوظائف الأساسية.
5. تشغيل الاختبار المستهدف.
6. تشغيل suite الكاملة.
7. إعادة السيناريو الحي نفسه.
8. إذا كان العيب `S0/S1`، إعادة المرحلة كاملة وكل السيناريوهات السابقة المتأثرة.

لا يغلق العيب بناءً على قراءة الكود فقط؛ يجب إثباته في Desktop الحي أو البيئة التي ظهر فيها.

## 10. التقرير المطلوب بعد كل مرحلة

يحتوي تقرير المرحلة على:

- release digest وschema وDesktop version.
- الأجهزة والمستخدمين وProfiles المستخدمة.
- السيناريوهات المنفذة وعدد المحاولات.
- pass/fail لكل حالة.
- latency percentiles ونسبة النجاح.
- عيوب `S0–S3` مع الأدلة.
- logs وtrace IDs المرتبطة بالفشل دون أسرار أو prompt كامل حساس.
- الإصلاحات المنفذة واختبارات regression.
- قرار الانتقال أو التوقف.

## 11. Production Acceptance Checklist

لا تعتمد المنصة للعميل حتى تتحقق جميع البنود:

- [ ] Golden journeys للأربعة ناجحة.
- [ ] correctness/evals ضمن الحدود.
- [ ] اختبار 30 رسالة واستمرارية السياق ناجح.
- [ ] UAT المتزامن بلا `S0/S1`.
- [ ] network reconnect وoffline exactly-once ناجحان.
- [ ] session refresh الطويل ناجح.
- [ ] restart للـAPI/Orchestrator/Runtime/Redis/Worker ناجح.
- [ ] provider outage يعطي failure واضحاً ويتعافى.
- [ ] MCP outage لا يعطل chat.
- [ ] Knowledge ACL وDLP وsync failure ناجحة.
- [ ] 12–24 ساعة soak دون leak أو degradation.
- [ ] السعة الآمنة مقاسة على عتاد مماثل.
- [ ] upgrade/rollback ناجحان.
- [ ] backup/restore ومتابعة المحادثات ناجحان.
- [ ] Pilot الداخلي 3–5 أيام مقبول.
- [ ] جميع `S0` و`S1` مغلقة ومعها regression tests.

## 12. القرار المهني

الخوف من أن يقول العميل «المنصة تفصل أو تخرب» لا يُغلق بزيادة unit tests وحدها. يُغلق بتشغيل نفس نسخة Desktop على أربعة مستخدمين مستقلين، مع بيانات متمايزة، واستخدام حقيقي طويل، وأعطال محقونة، ثم منع الإصدار عند أي فقد أو خلط أو عدم تعافٍ.

الترتيب الإلزامي المقترح هو:

1. Golden journeys.
2. Agent correctness.
3. Long-conversation continuity.
4. 4-user live UAT.
5. Failure injection.
6. Session longevity.
7. Soak and capacity.
8. Upgrade/restore.
9. Internal pilot.

بعد نجاح هذا التسلسل يمكن إعطاء العميل وعداً واقعياً ومدعوماً بالأرقام: المنصة لا تعتمد على أن «كل شيء يبدو شغالاً»، بل على بوابات قبول تمنع تسليم أي إصدار يضيّع رسالة أو يخلط مستخدماً أو يتوقف دون تعافٍ.
