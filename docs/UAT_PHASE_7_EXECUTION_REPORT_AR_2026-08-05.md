التاريخ: 2026-08-05

النطاق: Dashboard + FastAPI + Agent Runtime + أربعة تطبيقات Desktop مبنية ومفتوحة فعلياً  

## 1. قرار المرحلة

نجحت المنصة في اختبار soak متواصل لمدة 12 ساعة مع أربعة موظفين مستقلين، من دون فشل محادثة أو restart لخدمة أو فقدان سياق أو workspace مؤقت متروك. لا يمنح هذا التقرير وحده Production Go النهائي؛ يبقى اختبار 24 ساعة بوابة إلزامية قبل أول عميل كبير، وتبقى المراحل 8–10 من الخطة.

## 4. الموارد والاستقرار

- جميع الخدمات بقيت `running` طوال 145 snapshot، وعدد restarts لكل خدمة يساوي صفراً.
- PostgreSQL: أقصى 9 connections، لا انتظار فعلي، لا ungranted locks.
- Redis: queue depth بقي صفراً، والذاكرة بقيت ضمن نطاق صغير ومستقر.
- Runtime temporary directories: أقصى 3 أثناء runs الفعالة، وصفر في النهاية؛ لا orphan workspaces.
- Agent runs المنشأة خلال نافذة المراقبة: 2,189 بحالة `completed`، ولا `running` أو `pending` في النهاية.
- Durable tasks خلال النافذة: 725 بحالة `succeeded`، ولا queued/running عالقة.
- Audit chain نجحت في كل snapshot من البداية إلى النهاية.
- Orchestrator استقر بعد warm-up؛ ميل آخر ست ساعات 0.034 MiB/ساعة.
- API استقر؛ ميل آخر ثلاث ساعات سالب، ولا نمو مستمر.
- ارتفاع Docker الظاهر للـRuntime ليس تسرب heap: بعد توقف الحمل كان `RssAnon` للعملية الرئيسية 45.7 MiB فقط، بينما قرابة 40 MiB كانت kernel slab قابلة للاسترجاع نتيجة إنشاء العمليات الفرعية. عدد PIDs عاد إلى 5 وtemp dirs إلى صفر.
- Worker ارتفع 13.7 MiB خلال 12 ساعة مع تناقص الميل إلى 0.42 MiB/ساعة في الساعة الأخيرة، بلا زيادة PIDs أو queue؛ يصنف warm-up/allocator bounded ضمن هذه المدة، ويجب إعادة قياسه في اختبار 24 ساعة قبل أول عميل كبير.
- نمو PostgreSQL إلى 96.6 MiB متوافق مع buffer/page cache؛ لا connections أو locks متراكمة.

## 5. العيب الحقيقي الذي ظهر والإصلاح

وجد الفحص النهائي approval قديم من اختبار fault injection سابق، انتهى زمنه في 2026-08-03 لكنه بقي `pending` لأن العامل انقطع قبل تنفيذ مسار انتهاء المهلة. لم يُنشأ هذا السجل أثناء soak، لكنه عيب حقيقي يخالف شرط عدم وجود approvals عالقة.

تم إصلاحه بأقل تغيير ممكن داخل recovery الدوري الموجود أصلاً:

- تحويل أي approval بحالة `pending` وتاريخ `expires_at` منتهٍ إلى `expired/deny`.
- إعادة metric `expired_approvals` من recovery لتسهيل المراقبة.
- لا تغيير في واجهة المستخدم أو التصميم أو صلاحيات MCP أو السلوك الأساسي.

### التحقق من الإصلاح

- اختبارات Durable Tasks: 13/13 ناجحة.
- كامل اختبارات Python: 92/92 ناجحة.
- اختبارات Desktop: 2/2 ناجحة.
- اختبار حي داخل worker: `expired_approvals=1`.
- حالة قاعدة البيانات بعد الإصلاح: `pending=0`، `expired=2`، `decided=1`.
- Worker وBeat أُعيدا من الصورة الجديدة ويعملان بصورة سليمة.
