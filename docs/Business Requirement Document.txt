
وثيقة متطلبات الأعمال (BRD) – مشروع Hermes Agent للشركة
الإصدار: 1.0
التاريخ: 2026-06-11
المالك: عبدالرحمن كرزون
الهدف: تحسين إنتاجية الموظفين باستخدام وكلاء ذكاء اصطناعي (AI Agents) بنسبة 5× إلى 10×

0. مراجعة تنفيذية وتعديلات إلزامية قبل التنفيذ
هذه الوثيقة صالحة كنطاق أعمال أولي، لكن التنفيذ يجب أن يبدأ بنسخة MVP مضبوطة قبل تعميم النظام على جميع الموظفين. الأولوية في الإصدار الأول ليست عدد القنوات أو كثرة الأدوات، بل إثبات ثلاث نقاط: عزل بيانات المستخدمين، تجربة دردشة مفيدة على ملفات محلية، وتحكم إداري واضح في الاستخدام والتكلفة.

قرارات تنفيذية معتمدة لهذه النسخة:

1. مدة الخطة الأساسية 12 أسبوعاً، وليست 8 أسابيع. يمكن ضغطها فقط بتقليل النطاق أو زيادة الفريق، ولا ينصح بضغط الأمان والاختبار.
2. الإصدار الأول يجب أن يدعم 5-10 مستخدمين تجريبيين أولاً، ثم 50 مستخدماً، ثم التوسع التدريجي إلى 400 موظف بعد قياس الأداء والتكلفة.
3. قراءة ملفات الجهاز المحلي يجب أن تكون انتقائية وآمنة: تجاهل ملفات الأسرار والمجلدات الثقيلة مثل .git و node_modules و venv و build و dist، وعدم إرسال كامل المشروع مع كل رسالة.
4. سياق الملفات يرسل كملخصات ومقاطع ذات صلة فقط، مع حد أقصى للرموز لكل رسالة. أي إرسال كامل للسياق مع كل طلب يعتبر مخاطرة تكلفة وخصوصية.
5. تحرير الملفات محلياً يجب أن يكون خلف موافقة المستخدم وبصيغة معاينة فرق التغييرات قبل الحفظ، وليس كتابة مباشرة على الملفات.
6. تلغرام و KPIs ليستا شرطاً لإثبات MVP. يمكن تنفيذهما بعد ثبات Backend و Desktop Client.
7. مؤشرات الإنتاجية يجب ألا تعتمد فقط على عدد الرسائل أو كلمات مثل "تم"؛ يجب إضافة تقييم يدوي/زر إنجاز واستبيان قصير حتى لا تصبح KPIs مضللة.
8. يجب إضافة سياسة خصوصية داخلية واضحة للموظفين تشرح ما يتم رفعه من ملفات، وما لا يتم رفعه، وفترة الاحتفاظ بالرسائل والسياق.

1. ملخص تنفيذي
يهدف المشروع إلى بناء نظام متكامل لإدارة وتشغيل وكلاء ذكاء اصطناعي مخصصين (Hermes Agents) لجميع موظفي الشركة (حتى 400 موظف)، مع ضمان:

عزل بيانات كل موظف عن الآخر.

تحكم مركزي للإدارة (إضافة/إزالة موظفين، تحديد صلاحيات، وضع حدود استخدام، مراقبة مؤشرات الأداء).

تشغيل 24/7 دون الحاجة لتثبيت متكرر أو إعداد لكل موظف على حدة.

قدرة الموظف على العمل على ملفات ومجلدات جهازه المحلي (مثل Codex أو Cursor).

قنوات متعددة للتفاعل: سطح المكتب (Electron)، وتلغرام (Gateway)، وويب (احتياطي).

ربط مزود النماذج (مثل Minimax) عبر مفاتيح API لكل موظف أو للشركة مع حصص.

2. نطاق المشروع
2.1 داخل النطاق (In-Scope)
تطوير خادم مركزي متعدد المستأجرين (multi-tenant) يدعم:

مصادقة JWT لكل موظف.

عزل البيانات عبر user_id في قاعدة البيانات.

واجهة برمجة تطبيقات (API) لإدارة الموظفين والوكلاء والمستخدمين.

لوحة تحكم المشرف (Admin Panel):

إضافة/إزالة موظفين (بريد، قسم، صلاحيات).

تعيين قوالب وكلاء مسبقة لكل قسم (تسويق، موارد بشرية، تقنية، مبيعات).

تعيين حدود يومية (عدد الطلبات، عدد الرموز token).

عرض لوحة مؤشرات أداء (KPIs) لكل موظف/قسم.

عميل سطح المكتب (Desktop Client) بتقنية Electron:

يعمل على Windows فقط (المرحلة الأولى).

فتح مجلد محلي وقراءة محتوى الملفات لبناء سياق المشروع.

إرسال الرسائل مع السياق إلى الخادم.

عرض المحادثات والردود.

تحديث تلقائي (auto-update) من الخادم.

تخزين محلي للرسائل في وضع عدم الاتصال (offline queue).

بوابة تلغرام (Telegram Bot Gateway):

ربط حساب كل موظف مع بوت تلغرام.

استقبال أوامر ورسائل وإعادة توجيهها إلى الـ Hermes Agent الخاص به.

إرسال الردود عبر تلغرام.

نظام قوالب الوكلاء (Agent Templates):

ملف YAML مركزي يحدد system_prompt، الأدوات (tools)، النموذج المناسب، والحدود لكل قسم.

يُطبّق على جميع موظفي القسم تلقائياً، مع إمكانية تخصيص فردي لاحقاً.

تكامل مع MiniMax API (أو أي مزود نماذج):

إدارة مفاتيح API لكل موظف أو للشركة.

توجيه الطلبات مع سياق المستخدم والمشروع.

2.2 خارج النطاق (Out-of-Scope – المرحلة الأولى)
دعم أنظمة تشغيل أخرى (macOS، Linux) – يضاف لاحقاً.

تكامل مع أدوات داخلية مثل Salesforce أو Slack – عبر Webhooks لاحقاً.

تحليل صوتي أو فيديو.

تطبيقات جوال (iOS/Android).

3. حالات الاستخدام الرئيسية (Use Cases)
الرقم	حالة الاستخدام	الوصف
UC-01	إضافة موظف جديد	المشرف يدخل البريد الإلكتروني والقسم، فيُنشأ حساب تلقائياً، ويُرسل رابط تحميل العميل وكلمة مرور مؤقتة عبر البريد.
UC-02	موظف يفتح التطبيق ويعمل على مشروع محلي	يفتح الموظف Hermes Agent على جهازه، يسجل الدخول، يضغط "فتح مجلد"، يختار مجلد المشروع، فيُقرأ محتوى الملفات ويُرسل سياق إلى الخادم مع كل رسالة.
UC-03	موظف يسأل الوكيل عن ملف معين	يكتب الموظف "لخص ملف main.py"، فيقوم الوكيل باستخدام السياق المحفوظ ويرد بالإجابة.
UC-04	مشرف يضع حداً يومياً لموظف	من لوحة التحكم، يحدد المشرف max_tokens=50000 لموظف معين، وعند تجاوزه يُرفض الطلب ويُرسل إشعار.
UC-05	موظف يرسل رسالة عبر تلغرام	يكتب الموظف "كم عدد عملاء الربع الأول؟" في بوت تلغرام، فيُرسل البوت إلى الـ Gateway، ثم إلى Hermes Agent الخاص به، ويعود الرد.
UC-06	عرض مؤشرات الأداء	المشرف يفتح لوحة KPIs ويرى عدد المهام المكتملة لكل موظف، جودة الردود، الأدوات المستخدمة، وقت الاستخدام.
4. المتطلبات الوظيفية (Functional Requirements)
4.1 نظام المصادقة والعزل
ID	الوصف
FR-AUTH-01	يجب أن يدعم النظام تسجيل دخول الموظفين باستخدام البريد الإلكتروني وكلمة مرور + JWT token.
FR-AUTH-02	كل طلب إلى API يجب أن يحتوي على user_id المُستخرج من التوكن، ويتم عزل البيانات بناءً عليه (لا يرى الموظف سوى رسائله وجلساته).
FR-AUTH-03	يمكن للمشرف تعطيل أي موظف فوراً عبر واجهة الإدارة.
4.2 نظام الوكلاء (Hermes Engine)
ID	الوصف
FR-AG-01	يوفر النظام نموذجاً (router) يختار نموذج الذكاء الاصطناعي المناسب بناءً على دور الموظف والقسم (مثلاً نموذج 14B للتسويق، 235B لتقنية المعلومات).
FR-AG-02	يدعم النظام قوالب وكلاء معرفة بصيغة YAML، يمكن للمشرف تعديلها مرة واحدة وتنطبق على جميع الموظفين (أو أقسام محددة).
FR-AG-03	كل وكيل لديه قائمة أدوات (tools) مثل: البحث على الويب، تحليل الحملات، استعلام قاعدة بيانات الموظفين، إلخ.
FR-AG-04	يتم تمرير سياق المجلد المحلي (الملفات المفتوحة) تلقائياً إلى الوكيل مع كل رسالة.
4.3 واجهة المشرف (Admin Panel)
ID	الوصف
FR-AD-01	يمكن للمشرف إضافة موظف جديد مع تعيين قسمه ودوره (بريد إلكتروني، اسم، صلاحية).
FR-AD-02	يمكن للمشرف إزالة موظف (تعطيل فوري وأرشفة الجلسات).
FR-AD-03	يمكن للمشرف تعيين حد أقصى لعدد الرموز (tokens) وعدد الطلبات يومياً لكل موظف.
FR-AD-04	يمكن للمشرف تغيير قالب الوكيل لأي موظف بشكل فردي أو لأقسام كاملة.
FR-AD-05	لوحة تحكم تعرض KPIs: عدد المهام المكتملة، متوسط وقت الاستجابة، عدد الطلبات، تقييم الردود (آلي أو يدوي).
FR-AD-06	يمكن تصدير تقارير KPIs بصيغة CSV أو PDF.
4.4 عميل سطح المكتب (Electron)
ID	الوصف
FR-DSK-01	يقدم العميل واجهة دردشة مع الوكيل، وشريط جانبي لاستعراض الملفات المفتوحة.
FR-DSK-02	زر "فتح مجلد" يفتح مربع حوار Windows لاختيار مجلد، ثم يفهرس الملفات النصية المسموحة فقط، مع استبعاد المجلدات والملفات الحساسة أو الثقيلة مثل .git و node_modules و venv و .env و build و dist، وبحد افتراضي 2MB لكل ملف قابل للتعديل من الإعدادات.
FR-DSK-03	يحتفظ العميل بفهرس وملخصات محلية للسياق، ويرسل مع كل رسالة المقاطع ذات الصلة فقط بدلاً من إرسال كامل محتوى المجلد.
FR-DSK-04	إذا كان الخادم غير متاح، يحفظ العميل الرسائل محلياً (IndexedDB) ويعيد محاولة الإرسال تلقائياً عند استعادة الاتصال.
FR-DSK-05	يتحقق العميل من وجود تحديثات عند بدء التشغيل كل 24 ساعة، ويحمّل التحديث في الخلفية، ويطبقها عند إعادة تشغيل التطبيق.
FR-DSK-06	دعم تحرير الملفات محلياً: يمكن للموظف طلب تعديل ملف، ويقوم الوكيل بإنشاء محتوى جديد، ويضغط الموظف "حفظ" لكتابة الملف.
4.5 بوابة تلغرام
ID	الوصف
FR-TG-01	لكل موظف يمكنه ربط حسابه بتلغرام عبر أمر /start <token> يحصل عليه من الإعدادات الشخصية.
FR-TG-02	البوت يستقبل الرسائل ويعيد توجيهها إلى API الخادم مع user_id المستخلص من توكن الربط.
FR-TG-03	يمكن للموظف من خلال تلغرام إرسال أوامر مثل /project لعرض المشروع الحالي، أو /files لقائمة الملفات المفتوحة.
4.6 ربط مزود النماذج (MiniMax Gateway)
ID	الوصف
FR-MM-01	يدعم النظام إضافة مفاتيح API لمزود MiniMax (أو OpenAI-compatible).
FR-MM-02	يمكن تعيين مفتاح عام للشركة مع حصص، أو مفاتيح فردية لكل موظف.
FR-MM-03	يتم تمرير السياق (رسائل الجلسة + محتوى الملفات) إلى واجهة MiniMax وفقاً للنموذج المختار.

المكونات الأساسية:

Backend: FastAPI (Python) مع Dependency Injection لعزل المستخدمين.

قاعدة البيانات: PostgreSQL (أو SQLite للمرحلة التجريبية) مع جداول: users, sessions, messages, kpis, agent_templates, user_settings, telegram_bindings, audit_log.

التخزين المؤقت: Redis لحصر المعدل (rate limiting) وجلسات العمل.

عميل سطح المكتب: Electron + React/TypeScript + Node.js fs لقراءة الملفات.

نشر الخادم: Docker Compose (خادم VPS واحد أو On-premise).
