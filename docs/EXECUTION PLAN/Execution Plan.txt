# Execution Plan: Mount Hermes Agent Runtime Into AgentSaaS

## Summary

Build Hermes as a separate Docker-managed execution runtime on the VPS, while the existing FastAPI platform remains the SaaS control plane. The admin dashboard becomes the only control surface: it installs/checks Hermes, creates and edits Hermes profiles, syncs `AGENTS.md`, `skills.md`, `soul.md`, manages profile API keys, mounts employees to profiles, tracks sessions, KPIs, costs, and rate limits.

Default decisions:

- Hermes runs as a separate internal Docker service.
- Admin dashboard owns full lifecycle: install, health check, restart, sync, repair.
- API keys default to profile-level keys, with optional employee override.
- Desktop app does not change unless later testing proves a contract gap.
- FastAPI keeps auth, employees, quotas, Telegram, sessions, dashboard, audit, and cost controls.
- Hermes owns agent execution, profile files, tools/MCP, runtime behavior, and future RL/evaluation hooks.

## Key Architecture

Current state:

- `AgentService` builds a prompt from database profile fields and calls MiniMax/OpenAI/Ollama directly.
- Profiles exist in the database as `agents_md`, `soul_md`, `skills`, `system_prompt`.
- Assignments exist as employee-to-profile mappings.
- No real Hermes runtime is currently mounted.

Target state:

```text
Admin Dashboard
      |
      v
FastAPI Control Plane
- auth
- employees
- profile CRUD
- assignments
- API keys
- quotas/rate limits
- sessions/history
- KPIs/audit/costs
- Hermes lifecycle UI
      |
      v
Hermes Runtime Adapter
      |
      v
Hermes Docker Service on VPS
- profile workspaces
- AGENTS.md / skills.md / soul.md
- MCP/tools
- model provider config
- agent execution
- run events
```

FastAPI must not become a privileged Docker shell. Add a small internal `Hermes Orchestrator` component/service that exposes only approved lifecycle actions to FastAPI:

- check installed
- install/pull image
- start/stop/restart
- health check
- sync profile
- delete profile workspace
- validate profile
- fetch runtime status/log tail

The orchestrator may use Docker Engine access. FastAPI calls it over an internal-only network with a shared secret or mTLS.

## Implementation Changes

### 1. Add Hermes Runtime Layer

Create a runtime abstraction around agent execution:

- `DirectLLMRuntime`: current MiniMax/OpenAI/Ollama behavior.
- `HermesRuntime`: new runtime that dispatches requests to Hermes service.
- `AgentRuntimeRouter`: chooses runtime per profile.

Profile default:

- New profiles use `runtime_type = "hermes"`.
- Keep `runtime_type = "direct_llm"` for fallback/testing.

Execution behavior:

- Chat, WebSocket, Telegram all continue entering through FastAPI.
- FastAPI resolves employee, active status, quota, profile, and API key before dispatch.
- For Hermes profiles, FastAPI sends a run request to Hermes with:
  - employee id/email
  - profile id/slug/version
  - session id
  - user message
  - project context
  - provider key reference or decrypted key via secure internal channel
  - quota/cost metadata
- Hermes returns streamed events and final output.
- FastAPI stores messages, tokens, cost, selected profile, run status, and audit data.

### 2. Add Hermes Installation And Health Control

Add a dashboard page: `Hermes Runtime`.

It must show:

- installed/not installed
- Docker image/tag
- running/stopped/unhealthy
- Hermes version
- last sync status
- profile sync errors
- queue/run health
- service logs tail
- buttons: Install, Start, Restart, Stop, Repair Sync, Check Health

Backend APIs:

- `GET /api/admin/hermes/status`
- `POST /api/admin/hermes/install`
- `POST /api/admin/hermes/start`
- `POST /api/admin/hermes/restart`
- `POST /api/admin/hermes/stop`
- `POST /api/admin/hermes/repair-sync`
- `GET /api/admin/hermes/logs`

Best practice:

- `install` pulls/creates the Hermes Docker service.
- Installation is idempotent.
- FastAPI never runs arbitrary shell commands.
- Only admin users can trigger lifecycle actions.
- Every action writes to audit log.
- The UI shows progress and failure reason.

### 3. Add Profile-To-Hermes Sync

Extend profiles so each SaaS profile maps to a Hermes workspace.

Database additions:

- `profiles.runtime_type`
- `profiles.hermes_profile_id`
- `profiles.hermes_workspace_path`
- `profiles.hermes_sync_status`
- `profiles.hermes_sync_error`
- `profiles.version`
- `profiles.last_synced_at`
- `profiles.provider_key_id`, nullable

Profile files generated from admin dashboard fields:

- `AGENTS.md` from `agents_md`
- `soul.md` from `soul_md`
- `skills.md` from `skills`
- optional `system_prompt.md` from `system_prompt`
- `profile.json` for metadata: slug, version, model, provider, allowed tools, limits

Sync rules:

- Creating a profile creates a Hermes profile workspace.
- Updating profile content increments version and syncs files.
- Deleting a profile disables it first; hard delete removes workspace only if no sessions depend on it.
- Failed sync leaves DB change saved but marks profile `sync_failed`.
- Chat cannot use a Hermes profile unless sync status is `synced`.
- Admin can click `Repair Sync`.

### 4. API Key Model

Use profile-level MiniMax/API keys by default.

Reason:

- A marketing profile, accountant profile, and IT profile may need different budgets/models/providers.
- Multiple employees can share the same specialized profile without duplicating provider setup.
- Employee-level override remains useful for VIP users, external contractors, or separate billing.

Database/API changes:

- Add `profile_api_keys` or generalize `api_keys` to support `owner_type = user|profile|platform`.
- Keep existing employee keys for backward compatibility.
- Resolution order:
  1. active employee override key for provider
  2. active profile key for provider
  3. platform fallback key, if configured
  4. reject request with clear admin-facing setup error

Dashboard changes:

- API Keys page supports owner type:
  - Profile key
  - Employee override key
  - Platform fallback key
- Profile edit page shows provider key status.
- Assignment page shows whether mounted profile has a valid key.

Security:

- Keys remain Fernet-encrypted.
- Never expose full keys after save.
- Audit create/update/rotate/delete.
- Allow key rotation without deleting profile.

### 5. Employee/Profile Mounting

Current assignments are close to the target and should become the source of truth.

Behavior:

- One employee can mount multiple Hermes profiles.
- One Hermes profile can be mounted to many employees.
- Priority controls default profile when no profile is selected.
- Disabled employee cannot run any profile.
- Disabled profile cannot be used by any employee.
- Assignment create/delete triggers Hermes access sync.

Admin UI improvements:

- Assignments page shows employee, profile, runtime, sync status, priority, provider key status.
- Employee detail shows mounted profiles.
- Profile detail shows mounted employees.

Runtime enforcement:

- Every chat/run request validates that the employee is assigned to the requested profile.
- If no profile is requested, use highest-priority active assignment.
- Store `profile_id`, `profile_name`, and `profile_version` on each session/run.

### 6. Sessions, Work Logs, KPIs

Add a first-class Hermes run record separate from chat messages.

New model: `agent_runs`

Fields:

- `id`
- `session_id`
- `user_id`
- `profile_id`
- `profile_version`
- `runtime_type`
- `status`
- `started_at`
- `ended_at`
- `latency_ms`
- `input_tokens`
- `output_tokens`
- `total_cost`
- `model`
- `provider`
- `tools_used`
- `mcp_servers_used`
- `error_code`
- `error_message`

New model: `agent_run_events`

Fields:

- `run_id`
- `event_type`
- `timestamp`
- `payload`

Dashboard:

- Sessions page shows conversation history plus Hermes run events.
- KPI page adds:
  - cost by profile
  - cost by employee
  - tokens by profile
  - sessions by profile
  - failed runs
  - tool usage
  - average latency
  - top employees by usage
  - profiles with highest cost
  - profiles with highest failure rate

Decision-maker dashboard:

- Total employees / active employees
- Active profiles / failed profile syncs
- Today’s sessions
- Today’s cost
- Token usage trend
- Profile utilization
- Error rate
- Top costly profiles
- Disabled or quota-blocked employees
- Hermes health status

### 7. Rate Limits And Quotas

Keep rate limiting in FastAPI, not Hermes.

Employee-level limits:

- max requests/day
- max tokens/day
- active/disabled status

Profile-level limits:

- optional max requests/day
- optional max tokens/day
- optional daily cost budget
- allowed models/providers

Resolution:

- A request must pass both employee limits and profile limits.
- Usage is recorded against employee, profile, provider key, and platform total.

Dashboard:

- Employee page controls employee limits.
- Profile page controls profile budget/model limits.
- API Keys page controls key budget/spend.
- KPI page shows limit pressure and blocked requests.

### 8. MCP, Skills, And Future RL

MCP should be implemented through Hermes, not directly inside FastAPI.

Profile settings:

- allowed MCP servers
- allowed tools
- approval-required tools
- skills list/content
- profile memory settings
- model/provider settings

Admin dashboard should manage MCP/tool access without terminal work.

Add later-phase pages:

- MCP Servers
- Tools
- Approvals
- Evaluations

For reinforcement learning, do not start with training. First build the data layer:

- feedback on responses
- admin review labels
- task success/failure
- profile version comparisons
- evaluation datasets
- score history per profile

Only after enough data exists, add RL/fine-tuning/export workflows.

### 9. Deployment Flow

VPS deployment target:

```text
nginx / HTTPS / WSS
frontend dashboard
FastAPI backend
PostgreSQL
Redis
Celery worker
Hermes Orchestrator
Hermes Runtime container
```

Startup behavior:

- FastAPI starts normally even if Hermes is missing.
- Admin dashboard shows Hermes as `not_installed`.
- Admin clicks Install.
- Orchestrator pulls/starts Hermes Docker service.
- Health status becomes `running`.
- Admin creates/syncs profiles.
- Employees can use assigned synced profiles.

Failure behavior:

- If Hermes is down, direct dashboard actions still work.
- Hermes-backed chat returns clear runtime unavailable error.
- Direct LLM profiles may continue working.
- Dashboard shows repair/restart actions.
- All failures are auditable.

## Implementation Phases

### Phase 1: Runtime Boundary

- Add runtime abstraction.
- Move current direct provider calls behind `DirectLLMRuntime`.
- Add `runtime_type` to profiles.
- Keep all current tests passing.
- No Hermes behavior yet except interface shape.

Acceptance:

- Existing chat, WebSocket, Telegram, profiles, assignments, and tests still pass.
- Direct LLM mode behaves exactly as current system.

### Phase 2: Hermes Orchestrator

- Add internal orchestrator service.
- Add Docker lifecycle commands through approved API only.
- Add admin Hermes Runtime page.
- Add status/install/start/restart/stop/repair APIs.
- Add audit logs for all lifecycle actions.

Acceptance:

- Fresh VPS can show Hermes not installed.
- Admin can install/start Hermes from dashboard.
- Health checks and logs are visible.
- Repeated install is idempotent.

### Phase 3: Profile Sync

- Add Hermes workspace mapping fields.
- Generate/sync `AGENTS.md`, `skills.md`, `soul.md`, metadata.
- Sync on create/update/delete/repair.
- Add sync status to profile UI.
- Block execution for unsynced/failed Hermes profiles.

Acceptance:

- Creating a dashboard profile creates a Hermes workspace.
- Editing profile files in dashboard updates Hermes.
- Failed sync is visible and repairable.
- Profile version is stored per session/run.

### Phase 4: API Key Ownership

- Add profile-level API keys.
- Keep employee override keys.
- Add platform fallback key.
- Implement key resolution order.
- Update dashboard API key UI.

Acceptance:

- Profile key works for all assigned employees.
- Employee override wins when present.
- Missing key gives a clear setup error.
- Keys are encrypted and never leaked.

### Phase 5: Hermes Execution

- Implement `HermesRuntime`.
- Route Hermes profiles to Hermes service.
- Stream Hermes events through existing chat/WebSocket paths.
- Persist agent runs and run events.
- Record tokens/costs/tool usage.

Acceptance:

- Assigned employee can chat with a Hermes profile.
- Unassigned employee cannot use that profile.
- Admin can see session, messages, run status, and events.
- Quotas are enforced before and after runs.

### Phase 6: KPIs And Admin Visibility

- Add profile/employee/provider cost analytics.
- Add Hermes health widgets.
- Add failed run/sync alerts.
- Add tool/MCP usage summaries.
- Add dashboard visualizations for decision makers.

Acceptance:

- Admin can understand usage, cost, failures, and profile performance without terminal access.
- KPI data is accurate from persisted run records.

### Phase 7: Production Hardening

- Add production Docker Compose.
- Add nginx HTTPS/WSS config.
- Add backup/restore validation.
- Add secrets rotation documentation.
- Add service-level health checks.
- Add deployment smoke tests.

Acceptance:

- Platform deploys on VPS with dashboard, backend, DB, Redis, Hermes, and orchestrator.
- Admin can install and manage Hermes from UI.
- Production smoke test validates dashboard login, Hermes health, profile sync, employee assignment, and one successful run.

## Assumptions

- Hermes Agent can run as a Docker service on the same VPS.
- Hermes will expose or can be wrapped with an internal API for profile sync and run execution.
- Admin dashboard should own full lifecycle without terminal usage.
- Profile-level provider keys are the default and best model; employee keys are overrides.
- Desktop app can keep its current API/WebSocket contract.
- FastAPI remains the security and business control plane.
- Hermes is trusted only as the execution engine, not as the source of tenant authorization, quotas, billing, or admin policy.
