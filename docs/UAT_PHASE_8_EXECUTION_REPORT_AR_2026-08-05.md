# تقرير تنفيذ المرحلة الثامنة — السعة والضغط الآمن

التاريخ: 2026-08-05  
الحالة: **PASS مع سعة اسمية موثقة**  

## 1. قرار المرحلة

السعة الاسمية الآمنة على العتاد والنموذج المختبرين هي **4 active agent runs متزامنة**. Burst من 8 runs نجح بنسبة 100% من دون errors أو timeouts أو فقد بيانات، لكنه يمثل أول نقطة تدهور واضحة لأن p95 تضاعف تقريباً؛ لذلك لا يعتمد 8 كحمل اسمي على إعداد النموذج الحالي.

هذا الرقم خاص بهذه البيئة. إذا كان تركيب العميل يستخدم API خارجياً أو model server مختلفاً، يجب إعادة نفس الاختبار وفق concurrency وrate limits الخاصة بالمزود قبل تثبيت رقم تجاري.

## 2. البيئة المختبرة

- CPU: Intel Core Ultra 9 285K، عدد 24 cores/logical processors.
- RAM: 127.5 GiB، والحد المرئي لحاويات Docker قرابة 62.53 GiB.
- GPU: NVIDIA RTX 5090 بذاكرة 32,607 MiB.
- النموذج: Qwen3.6-27B-MTP-GGUF محلي.
- إعداد خادم النموذج الحاسم: `--parallel 1` وcontext يساوي 196,352.
- أربعة حسابات موظفين مستقلة: Accounting وMarketing وHR وIT.
- النقل: REST وWebSocket في الدفعة نفسها.
- الأحمال: short وlong وKnowledge، مع اختبار MCP حي مستقل عبر WebSocket.

## 3. منهج القياس

تم تشغيل ثلاث دفعات متتالية، في كل دفعة 4 runs تبدأ بفارق أقل من 4 ms، مع تدوير نوع الحمل وREST/WebSocket بين الموظفين. بعدها نُفذ burst من 8 runs مستقلة. توقف التصعيد عند أول تدهور أكبر من 50% منعاً لاختبار تدميري غير مفيد.

| المستوى | العينات | النجاح | p50 | p95 | Max |
|---|---:|---:|---:|---:|---:|
| 4 — الدفعة 1 | 4 | 100% | 11,202 ms | 14,988 ms | 14,988 ms |
| 4 — الدفعة 2 | 4 | 100% | 8,767 ms | 15,434 ms | 15,434 ms |
| 4 — الدفعة 3 | 4 | 100% | 10,812 ms | 14,742 ms | 14,742 ms |
| **4 — مجمّع** | **12** | **100%** | **10,101 ms** | **14,988 ms** | **15,434 ms** |
| 8 — Burst | 8 | 100% | 14,756 ms | 31,443 ms | 31,443 ms |

نسبة ارتفاع p95 عند 8 مقارنة بالسعة الاسمية: **109.8%**. هذا هو degradation point.

| المستخدم | العينات | المتوسط |
|---|---:|---:|
| Accounting | 3 | 9,782 ms |
| Marketing | 3 | 11,635 ms |
| HR | 3 | 9,897 ms |

أعلى متوسط يزيد على الأدنى بنحو 18.9% فقط مع اختلاف أحجام prompts، ولا يوجد مستخدم محروم أو failed. عند burst 8 ظهرت موجة انتظار ثانية ووصلت الطلبات الأثقل إلى 21–31 ثانية. هذا متوقع من model server ذي `parallel=1` وليس lock أو queue عالقاً في FastAPI أو DB.

## 8. توصية sizing

### عند استخدام النموذج المحلي الحالي

- اعتمد 4 active runs كحد اسمي لهذا الخادم.
- اسمح بـ8 كـburst قصير فقط إذا كان p95 قرابة 31 ثانية مقبولاً للعميل.
- لا ترفع parallel عشوائياً: النموذج يشغل قرابة 31.2 GiB من VRAM مع context كبير جداً، لذلك يلزم أولاً تخفيض context/اختيار quantization مناسب أو إضافة GPU ثم إعادة الاختبار.

### عند استخدام API خارجي — وهو السيناريو المرجح

- الرقم الحالي لا ينقل إلى المزود الخارجي.
- يجب أن تساوي concurrency المتعاقد عليها لدى المزود الحمل الاسمي المطلوب، مع headroom للـburst.
- أعد المستويات 4 ثم 8 ثم التصعيد الآمن على اتصال العميل الفعلي، وسجّل rate-limit وp95 لكل مزود/model.
